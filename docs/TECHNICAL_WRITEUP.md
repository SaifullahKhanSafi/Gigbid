# A perfect decision score was GigBid's least useful result

GigBid is a freelancer copilot that searches for suitable work, connects requirements to portfolio evidence, drafts a proposal, and waits for approval. Building the local product produced a surprisingly uncomfortable result: the handwritten workflow classified every job in its small orchestration comparison correctly, while most of its drafts still stopped at a Critic gate. The first number looked excellent in a table. The second described whether somebody could actually use the product. Understanding that gap changed how the system was evaluated, how claims were verified, and what the final report was willing to say. The work used local open models, explicitly fictional freelancer portfolios, and an attributed historical job snapshot for pricing. AI coding assistance is disclosed separately.

The headline accuracy came from a system comparison on fifty synthetic development jobs. A single ReAct baseline reached 58% bid-or-skip accuracy, the corrected prebuilt supervisor reached 30%, and the handwritten graph reached 100%. Those figures are real measurements, but their meaning is narrower than the ordering suggests. The graph combines model calls with explicit skill-coverage, risk and budget rules. The synthetic labels were generated from related definitions. An agent that recognizes those rules has an advantage before it writes a sentence. Calling that result evidence that multi-agent reasoning generally beats a single agent would confuse an experimental convenience with a discovery. The raw rows and failure accounting remain in [architectures.json](../evals/results/architectures.json).

The same experiment made the product limitation visible. The uniform small-model handwritten run ended with nine skipped jobs and forty-one needs-attention states. Its decisions were correct against the generated labels, but its Critic did not clear the proposed drafts. Nothing was sent. A separate real local demonstration using the stronger deployed writer did reach approval and handle a synthetic client reply, but one successful demonstration is not a broad quality result. This distinction matters because a durable workflow can fail safely and still fail to help its user. Decision accuracy, draft readiness, evidence grounding and actual marketplace response are separate outcomes. Combining them into a single attractive quality score would hide the point at which the freelancer's work stops.

Retrieval produced a smaller but similarly useful surprise. The system implements whole-job dense search, requirement decomposition, BM25/dense reciprocal-rank fusion, cross-encoder reranking, outcome-aware ranking and a corrective retrieval graph. On the shared synthetic development set, baseline dense project Recall@5 was 0.9595; decomposition reached 0.9794. Decomposition also had the highest nDCG@10, so it became the provisional configured choice. Adding a cross-encoder did not beat it. That does not show that cross-encoders are unhelpful. It shows that this corpus rewards identifying the separate explicit requirements more than making a more expensive relevance judgment over already similar candidates. Corpus construction, gold definitions and the returned unit of evidence all influence what a retrieval result means. [retrieval.json](../evals/results/retrieval.json) includes persona and job-type breakdowns.

That corpus deserves a candid explanation. Its freelancer histories, reviews, project renditions and proposal outcomes are fictional. Jobs and portfolios share a skills ontology and recurring task patterns. Project-level evaluation deliberately collapses equivalent case-study, README and code renderings, which avoids counting one project as several independent successes but makes the task easier than arbitrary sentence retrieval. Historical proposal outcomes were independent synthetic draws, so an outcome boost had little trustworthy signal to learn. Real Kaggle job records were kept separate and used for historical hourly pricing statistics; they did not magically supply freelancer credentials, risk labels or successful proposal outcomes. The data card records attribution, license, cleaning and the chronological split. Good provenance here prevents a polished demo from borrowing credibility from data it does not possess.

The proposal writer therefore has a deliberately constrained job. It proposes an approach, while experience enters as an exact approved fact or a verbatim source quotation with an evidence ID. A verifier labels claims and removes unsupported or partly supported assertions before Critic. This is less expressive than trusting a model to paraphrase every project convincingly. It also makes a concrete source inspection possible: opening a sentence shows the item that supports it, and deleting that item can invalidate a previously approved draft. The cost is false rejection. A conservative grammar can discard a harmless plan that begins in an unexpected way. Consequently the report calls these verifier-rejected statements, not independently proven hallucinations. Human calibration is still needed before claiming semantic verification accuracy.

Tool design gave a more straightforward tradeoff. Forty known-call tasks were tested against fine-grained tools, a coarse dispatcher and rewritten descriptions. Rewritten descriptions reached 100% tool-selection accuracy, compared with 87.5% for the fine set and 70% for the dispatcher. Argument accuracy remained lower than selection accuracy. The clearer descriptions also used more prompt tokens. These were JSON selection tasks, so the finding is intentionally not advertised as a native tool-call benchmark. Actual MCP requests were tested separately through in-memory clients and the official Inspector. The practical lesson was to keep capabilities distinct, document required fields, and give each role only the named tools it needs. A smaller tool list is not automatically an easier tool interface. [tools.json](../evals/results/tools.json) preserves every task output.

Several failures were ordinary integration mistakes rather than mysterious model behavior. The first async tests were skipped because a plugin was missing; installing it exposed real bugs. Entering an MCP connection context lazily inside a parallel graph node violated task ownership when the gateway later closed it. A supervisor produced no final structured field because its outer state schema omitted that channel. Both problems could have been misreported as unreliable agents if only the final score had been retained. Instead, the code was corrected, the relevant checks rerun, and initial failures preserved separately. Likewise, generic JSON mode let the smallest writer truncate or misformat its response. Explicit schemas repaired structured validity without establishing that the model had become a better proposal writer.

The safety experiment was less reassuring. Delimiting job text and adding a stronger instruction did not reduce disclosure of a synthetic canary in the small probe suite. Control and prompt-only conditions both disclosed it in sixty percent of cases. A follow-up that kept the unnecessary private value out of model input had no literal or base64 disclosures on those same attacks. That is context minimization, not improved obedience, and it does not protect sensitive task data that genuinely must enter context. The actual application follows that boundary: OAuth credentials remain encrypted in tools rather than appearing in prompts. Text risk detection is useful triage, but exact-content write authorization is what prevents an instruction in a job post from spending Connects. [attacks.json](../evals/results/attacks.json) and [secret_isolation.json](../evals/results/secret_isolation.json) keep the negative result visible.

Approval itself needed more than a button. A saved LangGraph interrupt stops the workflow, but a tool server must independently reject an unapproved mutation. GigBid signs a grant for the tenant, action and canonical payload hash. Editing the draft changes that hash and requires another review. A stable idempotency key binds the mutation to an atomic receipt and fictional-wallet debit, so a worker replay cannot spend twice. Evidence is re-read immediately before dispatch. The browser tests exercise approval after refresh, rejection, edited reapproval, onboarding, an unavailable-service banner and mobile layout. Those tests use explicit model doubles to isolate application behavior. The recorded local demo separately uses real models. Neither form of validation substitutes for the other.

Deployment exposed another boundary between a working project and a complete assignment. The local application, MCP services and separate worker run on the available machine. Compose and Render configuration are prepared, but a public deployment needs durable state and a reachable model endpoint; a cloud service cannot call this laptop's localhost. The official instructor simulator, policy update and hidden runner were not supplied, so official reply and hire rates remain unavailable. The recorded demo uses fixture replies. A later, separately authored model-client experiment found more replies for grounded proposals but no improvement in hires; its uncalibrated synthetic judgments are not official outcomes. Human calibration and blind ratings also remain blank until real reviewers perform them. A report that fills those gaps with synthetic proxies would be more complete-looking and less useful.

The most useful outcome was therefore a change in what counted as progress. A perfect decision table became a reason to inspect label construction. A failed Critic became a visible product state rather than a reason to bypass approval. A weaker retrieval addition stayed in the results instead of being removed from the story. The next experiment should use independent relevance labels and real human proposal judgments, followed by the official simulator when available. Until then, the shipped local system is an inspectable development product with explicit limits. Its strongest claim is that every reported number has a source and every outgoing action has a review boundary, not that a team of agents has already learned how to win freelance work.
